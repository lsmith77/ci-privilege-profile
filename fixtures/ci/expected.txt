# What each fixture repository must classify as, in both scopes:
#
#   <case> <pr-primary> <pr-flags> [<repo-primary> <repo-flags>]
#
# The first pair is the pull-request scope: only what a contributor's own pull
# request runs, which is the figure the classification exists to produce. The
# second is the whole repository, every pipeline file. A row that gives one
# pair stands for both: spelling identical columns out twice would read as a
# distinction being drawn where there is none.
#
# Checked by `python3 -m ciprofile --fixtures` and by ./test.sh. Entirely
# offline: each case is a synthetic repository tree, laid out as it would be
# on a forge, because the *path* is what decides which grammar a file is
# read with (.github/.forgejo/.gitea workflows vs .gitlab-ci.yml).
#
# Flags are compared as a set, so the order here does not matter. Adding a
# signal to the rule tables that moves one of these lines is the point of the
# table: it makes the blast radius of a table edit visible in a diff.
#
# Every case below that exists to pin a *class* declares a pull-request
# trigger, so the class is pinned in the scope the headline is quoted from and
# not only in the one that is not. Between them they also use each `on:` shape
# the parser handles (flow sequence, scalar, block mapping, block sequence,
# a nested `types:`, the quoted `"on":`), so the corpus of fixtures exercises
# the trigger reading as a side effect of pinning the classes.

self-contained              self-contained          self-contained,assumes-toolchain
forgejo-location            self-contained          self-contained
read-credential             read-credential         read-credential,credentials-test-time
writes-outward              writes-outward          writes-outward,credentials-unclear
acts-on-forge               acts-on-forge           acts-on-forge,uses-forge-token,credentials-reporting-only
special-env                 special-env             special-env
matrix-os                   special-env             special-env
gitlab                      writes-outward          writes-outward,assumes-toolchain,credentials-unclear
no-pipeline                 no-pipeline             no-pipeline

# Every run step is one `./pretest.sh`, so a contributor can reproduce it
# locally. The shape flag rides alongside the class, never replaces it.
thin-wrapper                self-contained          self-contained,thin-wrapper

# Why the scope exists. A pull-request check that only lints, beside a release
# workflow that publishes: read as one set of files the repository is
# writes-outward and the release workflow's `&&` takes thin-wrapper away too,
# so neither reading of the contributor's own pipeline survives. Scoped, both
# do. Nearly every mature project carries a release or deploy workflow, so the
# shape is the common case rather than an edge.
pull-request-scope          self-contained          self-contained,thin-wrapper                             writes-outward          writes-outward,credentials-unclear

# A repository with a pipeline and nothing a pull request triggers. Its own
# state, counted apart from no-pipeline: one project does no CI, the other does
# CI a contributor never sets off, and folding them together inflates
# no-pipeline, which is among the figures most likely to be quoted.
no-pull-request-trigger     no-pull-request-trigger no-pull-request-trigger                                 writes-outward          writes-outward,credentials-unclear

# The case the separate tally exists for: a `pull_request_target` workflow
# whose primary class is `self-contained`. Nothing about the privileged trigger shows
# up in the distribution table, which is why it is counted on its own.
pull-request-target         self-contained          self-contained,thin-wrapper,uses-pull-request-target

# And its over-claim. The same string in a `run:` step is not a trigger, so
# the flag must stay down: the trigger figure is one of the few exact enough
# to quote outside, and it is held to what the `on:` declaration says.
pull-request-target-in-run  self-contained          self-contained,thin-wrapper

# What `self-contained` does not mean. No secret, no outward write, no runner
# label. And node still has to be on the runner before `npm test` starts. The
# environment dependency is reported beside the class and ranks nothing,
# because what a shared runner image must carry is a separate question from
# what privilege a host must grant.
assumes-toolchain           self-contained          self-contained,assumes-toolchain

# The two halves of the forge-token split, which is the judgement that most
# moves the headline distribution. `forge-token-no-write` is the whole of the
# carve-out's effect: a stricter reading would call it read-credential. The
# other half carries acts-on-forge on its own forge-write signal, so the
# carve-out decides nothing there, and it is written in GitLab's grammar,
# where `CI_JOB_TOKEN` is recognised by variable name because there is no
# `secrets.` namespace to name it in.
forge-token-no-write        self-contained          self-contained,uses-forge-token
forge-token-with-write      acts-on-forge           acts-on-forge,uses-forge-token,credentials-unclear

# The two halves of the name scan, which is all the evidence there is for a
# credential referenced as a plain shell variable. `cache-key` is the case
# NOT_CREDENTIAL exists for: a `_KEY` name that is ordinary data, and nothing
# a contributor has to be given. `credential-by-name` is the same spelling
# where the name does mean a credential, and it must keep saying so.
cache-key                   self-contained          self-contained
credential-by-name          read-credential         read-credential,credentials-unclear

# The `push:` input, which is the whole of the evidence that
# docker/build-push-action publishes anything. `build-push-conditional` is the
# expression form GitHub's own starter workflow for the action emits (one
# workflow that builds on a pull request and publishes on main), and a
# conditional push is still a push; its ghcr.io login is why the forge token
# rides along. `build-push-build-only` holds the two readings that are not a
# push: `push: false` stated outright, and the input left off, which the
# action treats the same way. The distinction decides whether a repository
# lands in self-contained or writes-outward, and in a corpus that is almost entirely
# GitHub Actions it decides it in bulk.
build-push-conditional      writes-outward          writes-outward,uses-forge-token,credentials-unclear
build-push-build-only       self-contained          self-contained

# What actions/github-script is used for, rather than what it can do. This
# body only logs and sets variables for later steps, so no forge call happens
# and the step is no evidence of one; `acts-on-forge` above is the same action
# with a `github.rest` call in its body. On the action's presence alone this
# would take the top class on the strength of a client the script never
# touches.
github-script-core-only     self-contained          self-contained

# A write whose only evidence is the permission. `packages: write` is a
# registry publish; `id-token: write` is the keyless path to a registry, a
# cloud account or a signature, and nothing else in the file can catch it,
# because the OIDC token the grant mints is exactly what replaces the
# credential a secret reference or a credential-shaped name would expose. Both
# write outward rather than against the forge API, so both rank writes-outward
# and neither is acts-on-forge.
packages-permission         writes-outward          writes-outward,credentials-unclear
id-token-permission         writes-outward          writes-outward,credentials-unclear

# The reporting-versus-test-time axis, which says what the privilege is FOR and
# never how large it is: every row above carries its value too, and none of
# them changed class to get one.
#
# `reporting-coverage-upload` is the case the axis exists for (unprivileged
# tests, one secret, and it reaches a coverage uploader), so it is
# read-credential and counted in the contributor-runnable figure all the same.
# `reporting-always` is the same conclusion from the weaker signal, where no
# table knows the tool and `if: always()` is the whole of the evidence.
# `reporting-pr-comment` is why the axis spans the classes rather than sitting
# inside read-credential: acts-on-forge, and as contributor-runnable as an
# self-contained repository, because the forge privilege buys a comment and nothing
# else. `acts-on-forge` above is the same finding reached through a
# github-script body whose only call posts a comment.
#
# `credentials-test-time-maven` is the inverse and decisive: the credential is
# what resolves the dependencies, so the pipeline does not run without it and
# no reporting reading is available. `read-credential` above is the npm
# spelling of it.
#
# `reporting-plus-unknown` is the asymmetry, and the most important row here.
# A recognised coverage upload sits beside one privileged step no rule
# recognised, and the scope is unclear rather than reporting-only: one
# unrecognised step is enough, because reporting-only is a positive claim about
# every privileged step in the scope. Let that row read reporting-only and the
# flattering answer wins by default for every tool the tables have never heard
# of, which is the failure this whole module is written against.
reporting-coverage-upload   read-credential         read-credential,credentials-reporting-only
reporting-always            read-credential         read-credential,credentials-reporting-only
reporting-pr-comment        acts-on-forge           acts-on-forge,thin-wrapper,credentials-reporting-only
credentials-test-time-maven read-credential         read-credential,assumes-toolchain,credentials-test-time
reporting-plus-unknown      writes-outward          writes-outward,credentials-unclear

# The neutral list, and the one edge it must not swallow. `neutral-plus-reporting`
# wraps a coverage upload in build plumbing (a checkout, a toolchain setup, a
# cache restore and save, an artifact upload) and still reads reporting-only:
# none of those consumes a privilege, so none of them is a privileged step
# nothing recognised. `actions/upload-artifact` is on the list and is the entry
# a reviewer will challenge, since an artifact is how a result leaves a run;
# the axis asks only whether a step consumes a privilege somebody has to grant,
# and that one consumes none. `neutral-handed-secret` is the edge: the same
# checkout handed a personal access token is judged on that token like any
# other step, so membership of the list can never swallow an explicit
# credential, and the scope is unclear with the coverage upload beside it.
neutral-plus-reporting      read-credential         read-credential,assumes-toolchain,credentials-reporting-only
neutral-handed-secret       read-credential         read-credential,credentials-unclear

# A grant nothing consumes is not a privilege a contributor needs. The
# `pull-requests: write` here is declared for a step that is not in the file,
# and nothing names the forge token either, so there is no step it could be
# scoping: recorded as `unused-grant` and deciding nothing, where before it
# alone held the repository out of the figure. No credentials-* flag follows,
# because the scope needs no privilege at all; the grant still ranks the
# class, which is the ladder's business and not this axis's.
unused-permissions-grant    acts-on-forge           acts-on-forge,assumes-toolchain

# Cloud authentication with the tests after it: not a record of the run, and
# not droppable, so the axis answers test-time instead of shrugging.
cloud-credential            writes-outward          writes-outward,assumes-toolchain,credentials-test-time

# Minting a forge token from a GitHub App is forge-side privilege, so the class
# is acts-on-forge, and the App's id and private key are secrets a contributor
# would have to be given, which is why the carve-out for the forge's own
# auto-minted token does not reach it. The axis stays unclear on purpose: the
# mint says what the token can do, never what it is for.
forge-app-token             acts-on-forge           acts-on-forge,credentials-unclear

# A `steps:` whose items sit at its own column. Legal YAML and common here, and
# read as an empty block it put the whole job's privilege in the frame, where
# no step could be held responsible for it. Attributed, the one credential
# feeds a code-quality upload and the scope is reporting-only.
steps-at-key-column         read-credential         read-credential,assumes-toolchain,credentials-reporting-only
